# Voice profile format

`tools/build-profile.py` turns `profiles/marble/voice.json` into
`firmware/qcom/marble-voice-active.bin`. The JSON stores the two GRAPH_OPEN
payloads and 24 ordered commands. Each payload and the final binary have a
SHA-256 digest. Configuration and calibration bytes are preserved verbatim.
The source contains no captured audio samples or response/device logs.

All binary integers are unsigned 32-bit little-endian. Records are packed;
APM payload parameter bodies carry their original eight-byte alignment.

## MVSA version 1

| Offset | Field |
| --- | --- |
| 0 | Magic `0x4153564d` (`MVSA`) |
| 4 | Version: 1 |
| 8 | Embedded MVOP byte length |
| 12 | Command count |
| 16 | Embedded MVOP, followed by command records |

## Embedded MVOP version 1

| Offset | Field |
| --- | --- |
| 0 | Magic `0x504f564d` (`MVOP`) |
| 4 | Version: 1 |
| 8 | RX GRAPH_OPEN payload byte length |
| 12 | TX GRAPH_OPEN payload byte length |
| 16 | RX payload, then TX payload |

MVOP is an embedded descriptor block. No separate OPEN-only firmware file
is installed.

## Command record

| Offset | Field |
| --- | --- |
| 0 | Type: OPEN=1, SET_CFG=2, REGISTER_CFG=3, PREPARE=4, START=5 |
| 4 | Graph: RX=0, TX=1 |
| 8 | Destination instance: APM=1, VCPM=4, or a declared module |
| 12 | Payload byte length |
| 16 | Increasing source sequence number |
| 20 | Reserved: zero |
| 24 | Payload bytes |

OPEN uses the corresponding embedded graph payload. PREPARE and START also
have no record payload. The source sequence number retains ordering and
identifies a failed command; gaps are allowed. MAP/UNMAP and teardown commands
are generated by the driver, with fresh addresses, handles, ports and tokens.

The kernel checks the 256 KiB profile limit, 64 KiB embedded-graph limit,
32-command limit, record bounds, supported commands, module/subgraph ownership,
calibration coverage and lifecycle ordering before issuing commands.
Calibration registration remains persistent until acknowledged teardown.

The builder rejects changed payload or binary hashes. To derive a different
profile, replace the relevant captured bytes and their digests together,
then assess firmware compatibility and test the physical path separately.
